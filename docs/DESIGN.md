## 1. Обоснование механизма отмены и выбора задержки `debounce`

### Механизм отмены запросов (`AbortController`)

Для предотвращения состояния гонки (race condition) и экономии сетевых ресурсов используется нативный `AbortController`.

- **Проблема:** При быстром вводе пользователя генерируется множество сетевых запросов. Если не отменять предыдущие запросы, ответ на старый запрос может прийти позже ответа на новый (из-за задержек сети). Это приведет к отображению неактуальных (устаревших) результатов, даже если пользователь уже ввел новый текст.
- **Решение:** `AbortController` создается при каждом изменении ввода. Его `signal` передается в опции `fetch`. Если ввод продолжается, для предыдущего контроллера вызывается метод `abort()`. Это гарантирует, что промис предыдущего запроса будет отклонен с ошибкой `AbortError`.
- **Обработка ошибок:** Ошибка `AbortError` намеренно игнорируется в UI (не показывается пользователю), так как это ожидаемое поведение системы при отмене, а не реальная ошибка.
- **Таймаут:** Для защиты от «зависших» запросов используется `AbortSignal.timeout()`. Возникающая при этом `TimeoutError` классифицируется отдельно от `AbortError`, вызванного намеренной отменой, что позволяет корректно показать пользователю сообщение о превышении времени ожидания.

### Выбор задержки `debounce`

- **Значение:** Задержка установлена в **300 мс** (допустимый диапазон 300–500 мс), задана в константе `SEARCH_DELAY_MS`.
- **Обоснование:**
  - Меньшие значения (например, 100 мс) приводят к слишком частым запросам, что увеличивает нагрузку на сервер и риск получения ошибки 429 (Too Many Requests).
  - Большие значения (например, 1000 мс) создают ощутимую задержку для пользователя (т.е. ситуацию, когда пользователь закончил ввод, но интерфейс все еще не реагирует).
  - Значение ~300 мс является оптимальным компромиссом: оно покрывает среднюю скорость печати человека, позволяя дождаться естественной паузы перед отправкой запроса, при этом сохраняя интерфейс отзывчивым.

## 2. Оценка сложности алгоритмов (Big O)

### Функция `mapCountryResponse`

- **Временная сложность:** $\mathcal{O}(N)$, где $N$ — количество элементов в массиве стран, возвращаемых API.
  - **Обоснование:** Функция использует метод массива `.map()`, который проходит по каждому элементу входного массива ровно один раз. Операции внутри колбэка (деструктуризация, присваивание, преобразование типов) выполняются за константное время $\mathcal{O}(1)$ для каждого элемента.
- **Пространственная сложность:** $\mathcal{O}(N)$, так как создается и возвращается новый массив преобразованных объектов той же длины, что и входной массив.

## 3. Принципы чистого кода (Clean Code)

В проекте сознательно применены следующие принципы:

1. **Принцип единственной ответственности (Single Responsibility):**
   - **Где применен:** Логика разделена на изолированные модули. `debounce` управляет только таймером, `searchCountries` отвечает только за сетевой запрос, `mapCountryResponse` занимается исключительно трансформацией данных, а `classifyError` определяет тип ошибки.

2. **Самодокументируемый код (Self-documenting code):**
   - **Где применен:** Использование понятных, описательных имен переменных и функций (например, `classifyError` вместо абстрактного `checkErr`, `isAbortError` вместо прямой проверки `error.name === 'AbortError'`). Это делает код читаемым без избыточных комментариев.

3. **KISS (Keep It Simple, Stupid) - Ранний возврат:**
   - **Где применен:** В функции `classifyError` и обработчиках ответов сначала проверяются граничные условия (например, `if (error.name === 'AbortError') return;`). Это позволяет избежать глубокой вложенности `if-else` (anti-pattern "callback hell" или "arrow code") и делает логику плоской и легко читаемой.

4. **Иммутабельность и чистые функции (Pure Functions):**
   - **Где применен:** `mapCountryResponse` является чистой функцией: она не мутирует входные данные, не имеет побочных эффектов (side effects) и для одних и тех же входных данных всегда возвращает идентичный результат. Это также критически важно для надежного модульного тестирования.

5. **Разработка через тестирование (Test-Driven Development, TDD):**
   - **Где применен:** Все ключевые функции (`debounce`, `searchCountries`, `mapCountryResponse`, `classifyError`) были покрыты тестами _до_ написания рабочей реализации (что подтверждается историей коммитов: `test: add failing tests...` - `feat: implement...`). Это гарантирует, что код изначально проектировался с учетом проверяемости и строгого соответствия контракту.
